# 개발규칙

상태: 유저가 합의한 규칙을 DOC-001에서 문서화. 문서 표현의 최종 확인 대기.

## 권한과 승인
- 유저가 방향·최종 기록·다음 작업을 결정한다. AI는 승인 범위만 보조한다.
- 요청 관련 읽기·불러오기·검색·현황 조회는 별도 승인 없이 수행한다.
- 변경 전에 대상 파일, 변경 내용, 제외 범위, 완료 조건, 검증 방법을 보고한다.
- 승인에는 보고된 파일의 생성·수정·검증·로컬 저장을 포함한다. 저장을 다시 묻지 않는다.
- 범위 밖 변경은 보류하고 추가 승인받는다. 임의 기능·편의성 코드·리팩토링을 추가하지 않는다.
- 임시 장비칸 크기, 능력치, 블록 색상·시험용 모양, 임시 이미지 적용은 허용된다. 값과 출처·설정 이유를 기록한다.
- 임시 이미지 사용 허용은 이번 문서 작업에 이미지 제작·다운로드를 추가한다는 뜻이 아니다.
- 조합식·새 스킬·지원 건물 등 미승인 기능까지 임의 설정하지 않는다.

## 작업 시작과 순서
1. 개발규칙 → task.md → 관련 기획·정의·UI 문서 → 직전 작업 기록을 읽는다.
2. 실제 파일과 비교한다. 충돌·불명확한 조건은 유저에게 확인한다.
3. 큰기획으로 전체 흐름·단계를 정리하고, 작은 내용별 문서를 연결한다.
4. 큰기획 승인은 전체 코드 구현 승인이 아니다. 현재 세부 작업만 보고·승인·실행한다.
5. 작업 결과, 검증 결과와 미실행 항목을 보고한다. 최종 확인은 유저에게 받는다.
6. Next To-Do는 제안이며 자동 실행하지 않는다.

## 응답과 문서
모든 응답은 독립된 markdown 코드 블록 5개로 제공한다.
- 1_대화기록.md: 요청과 결정 요약.
- 2_사전확인.md: 목표·대상·제외·완료 조건과 승인.
- 3_작업일지.md: 날짜·실제 변경·검증·다음 제안.
- 4_정의문서.md: 객체·변수·UI·규칙 정의 및 상태.
- 5_버전관리.md: 로컬·커밋·원격 저장 상태와 필요한 명령.

어려운 본문 바로 아래에 같은 의미의 `↳ 쉽게 말하면:` 풀이를 붙인다. 전문가용/비전공자용 문서를 분리하지 않는다. 쉬운 문장은 불필요하게 반복하지 않는다.

채팅 출력과 파일 저장을 구분한다. 파일 저장은 승인 범위에서 수행한다. 새로운 세부 내용을 확정·임시·보류로 구분하고 유저 최종 확인 여부도 따로 기록한다.

## UI
- 이미지에 라벨·구역 표시를 우선 사용하고 짧은 설명을 연결한다.
- 위치 지정 없이 AI가 최종 배치를 상상하여 구현하지 않는다.
- 기존 라벨로 대상이 특정되면 좌표를 반복해서 요구하지 않는다.
- 기술 좌표·앵커가 필요하면 AI가 제안하고 확인받는다.
- 이미지에 보이는 버튼·수치가 자동으로 확정 기능이 되는 것은 아니다.
- 실제 이미지·라벨 관리 형식은 진행 중 유저 피드백으로 조정한다.

## 기술·검증
- 엔진·스택이 미정이면 선택지를 설명하고 유저 선택을 기다린다.
- 검증은 승인 범위와 관련된 것만 수행한다. 하지 않은 검증을 성공으로 기록하지 않는다.
- 구현 완료·검증 완료·유저 확인 완료·GitHub 저장 완료를 구분한다.

## GitHub
- 기본적으로 유저가 커밋·푸시한다. 다만 유저가 직접 실행을 요청하면 AI가 지정 저장소에 해당 작업의 커밋·푸시까지 수행할 수 있다.
- 2026-11-02 유저가 초기 기획 문서의 GitHub 저장을 AI에게 직접 요청했다. 이 요청에 따라 초기화·원격 연결·커밋·푸시를 수행한다.
- 다음 작업 전에 이전 변경의 원격 저장 상태를 확인한다.
- 미저장이면 저장 절차를 먼저 안내하고 푸시 완료 확인을 기다린다.
- `다음 작업 진행해`는 푸시 완료의 증거가 아니다.
- GitHub 상태 확인이 불가능하면 불명으로 보고한다. 로컬 저장만으로 원격 저장을 주장하지 않는다.
- 관계없는 파일을 포함하지 않도록 변경 파일을 지정한다. 저장소·원격·브랜치 확인 후 명령을 만든다.
