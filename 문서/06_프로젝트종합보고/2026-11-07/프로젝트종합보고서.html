2. 프로젝트 개요와 추진 배경

2.1 기획에서 확인되는 출발점

[확인] 초기 HWP는 실시간 진행, 격자형 인벤토리, 병사·영웅 배치, 소환과 장비 투자 사이의 판단을 중심에 둔다. 40웨이브와 4회 보스 구간, 영웅·장비 성장, 상품·외형 판매 아이디어도 기획에 존재한다. 다만 시작한 개인적 배경, 창업 목표, 확보한 수요 조사나 매출 계획은 확인되지 않는다. [E01]

[제안] 해결하려는 사용자 수요는 “반복 소환만으로 끝나지 않고, 내가 정리한 장비와 배치가 전투 결과를 바꾼다는 경험”으로 설명하는 것이 적절하다. 이는 프로젝트의 제품 가설이며 시장 검증 결과가 아니다.

2.3 최종 범위의 현실적인 정의

[제안] 단기 제품 범위는 “첫 보스까지 처음 이용자가 스스로 도달하고, 패배 후 보상·성장을 이해하며 다시 도전할 수 있는 체험”으로 설정한다. 상용 범위는 이 검증 이후 별도 확정한다. 40웨이브 완주, 다양한 보스·영웅, 앱 배포, 계정·결제를 한 번에 완료 조건으로 묶으면 현재 병목과 검증 목적이 흐려진다.

[판단] 이 구조는 시제품 반복 개선과 웹 배포에 적합하다. 계정 동기화·운영·결제·다중 기기 저장이 필요한 사업 모델을 택하면 추가 서버/플랫폼 설계가 필요하다. 현재 파일 수나 코드량만으로 사용자 동시 접속 규모·FPS·서버 비용을 추정할 수 없다.

7.1 단계별 실행 계획

아래 기간은 확정 일정이 아닌 검토용 추정이다. 전담 구현자 1명, 기획/아트 피드백 병행, 현재 기술 유지, 신규 대형 아트·계정·결제 제외, 주 단위 의사결정이 가능하다는 전제다. 외주 대기·사용자 모집·스토어 심사는 포함하지 않는다. 실제 투입 시간 확인 후 다시 산정한다.

단계·제안 범위목표·작업우선순위·선행 조건필요한 자원산출물·완료 기준
단기 A: 1~2주 검토 범위진형 규칙, 영웅 ID·출시 체험 범위, 기기 목록 확정P0 / 담당자 가용시간·정식 명단기획+개발, 대표 기기결정 기록, 공통 진형 데이터, 첫 보스 체험의 명시적 합격 기준
단기 B: 2~4주 검토 범위첫 보스 체험·강제 튜토리얼·핵심 모바일 입력·복귀 안정화P0/P1 / A·배치 확정개발+QA, 제한된 테스트 사용자도움 없이 소환/구매/장착/조합, 패배/복귀/재도전, 저장 중복 없음
중기 C: 3~6주 검토 범위테스트에 따라 경제·영웅 연결·보스 차별화·아트 채택 보완P1 / 체험 데이터·콘셉트 결정시스템 기획·아트·개발·QA로비/전투 수치 일치, 채택 리소스 검수표, 난이도 곡선·변경 전후 관찰
중기 D: 범위 결정 후 별도 산정최종 웨이브·보스·완주 보상, 최소/권장 기기 대응P1 / 콘텐츠와 플레이 시간 확정콘텐츠 제작·QA목표 구간 완주/패배 모두 결과·보상·성장으로 연결
장기 E: 시제품 검증 후 산정앱 출시 방식·계정·수익 모델·운영P2 / 유지·결제 의향·예산 근거플랫폼·서버 필요 역할·운영출시 체크리스트, 지급/복구/지원, 권리·기기·스토어 검증

A~C의 6~12주는 위 전제하의 작업 묶음 합계 예시이며 출시일이 아니다. 병행 범위와 피드백 지연에 따라 달라진다. 산정은 기능 결정·구현·회귀 확인을 묶은 업무량 가정으로, 과거 처리 속도나 커밋 수를 시간으로 환산하지 않았다.

7.3 다음 단계로 넘어가는 조건

  • 다음 시제품 검증: 첫 보스까지의 범위·진형·기본 조작이 문서와 실제 동작에서 일치하고, 저장·결과·보상 경로의 치명적 결함이 없어야 한다.
  • 콘텐츠 확대: 주요 조작의 반복 막힘이 해소되고, 재도전·장비 선택의 이유를 사용자 관찰로 설명할 수 있어야 한다.
  • 출시 준비: 최종 분량·기기·플랫폼·수익 모델 확정, 아트·음원·효과 이용 조건 정리, 운영·복구·품질 기준 충족이 필요하다.

9.1 기준 프로젝트와 작업 공간

[확인] 실제 기본 브랜치는 main이며 연결된 작업 영역은 총 8개다. 시작 시 main은 origin/main과 같은 e31227b였다. 모든 제작 작업은 미커밋 산출물이나 별도 변경을 포함하므로 전체 브랜치를 무조건 병합하지 않았다. 각 HEAD·상태·원본 위치는 통합 현황에 기록했다.

Orca 화면에서는 이름 8개와 부모 관계 4개를 정리했다. 실제 폴더·브랜치 이름·진행 상태를 바꾸거나 작업을 보관/삭제하지 않았다. 지원 기능 범위에서 의미 있는 이름과 계층을 정리했으며, 임의의 화면 순서 재배열은 지원 명령이 없어 기존 순서를 유지했다. 변경 전후 JSON을 제공하므로 메타데이터를 복원할 수 있다.

  • 모든 수집 이펙트 프레임의 육안 승인·전체 외부 소재 권리 검토: 이번에는 작업 기록·카탈로그·출처를 조사했고 모든 공방 검사를 재실행하지 않았다.
