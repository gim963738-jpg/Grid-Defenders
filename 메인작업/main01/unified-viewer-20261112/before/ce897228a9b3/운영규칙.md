# MAIN01 운영 규칙 — v4.1 / 2026-11-12

근거: 사용자의 운영 개편·12단계 직접 지시와 최신 진행 응답 구분 문구 `################진행############` 지정. 이 파일이 현재 운영의 단일 원본이다. 최신 사용자 지정 응답 방식이 이전의 물리적 클릭 출처 인증 요구를 대체한다.

## 0. 모든 신규 작업의 12단계 — 순서 생략 금지

1. **요청 수신**: 최초 요청과 나누어 들어오는 추가 설명을 통합 명세에 빠짐없이 수합한다.
2. **이해 내용 브리핑**: 목표, 원본, 결과물 개수·각도·형식, 유지할 것, 변경할 것, 실제 동작 순서, 확인할 부분과 미확정 사항을 **아주 상세하고 쉬운 말**로 사용자에게 설명한다. 짧은 재진술로 끝내지 않는다. 브리핑 내용과 실제 제시 근거를 같은 명세에 연결한다.
3. **진행 선택지 대기**: `################진행############` / `보류` 선택지와 기본 직접 입력란을 제공한다. 현재 확인 질문에 대한 해당 구분 문구의 실제 단독 응답을 진행 승인으로 받는다. 일반 대화의 ‘진행’·긍정 표현은 승인으로 처리하지 않는다.
4. **전문 프롬프트 발송**: 응답으로 확정된 범위에 맞춘 전문 프롬프트를 담당에게 전달한다. 전달용 작성·번역이 확정된 의미를 바꾸면 발송하지 않는다. 프롬프트 초안은 브리핑 준비 시 작성할 수 있으나 승인 응답 전에는 실행·발송하지 않는다.
5. **1차 결과물 대면**: 결과가 나오면 기본적으로 자체 미적 합격·불합격 선별이나 몰래 재제작을 하지 않고 사용자에게 먼저 보여준다. GC9처럼 **이번 제작 전에 확고하게 확립된 검수 기준**이 실제로 있는 경우만 명세에 근거를 연결해 예외로 적용한다. 단순히 GC9라는 이름이 있다는 이유로 예외 처리하지 않는다. 파일 접근 가능 여부 확인은 결과물을 임의로 선별하는 판단과 구분한다.
6. **피드백 수신**: 사용자의 수정 의견을 원문 그대로 수합한다. 여러 발화를 마지막 한 문장으로 대체하지 않는다.
7. **피드백 확인 선택지**: 적용할 피드백 전부를 사용자에게 제시하고 `피드백 받음(적용)` / `보류` 선택지와 기본 직접 입력란을 제공한다. 현재 피드백 묶음에 대한 해당 선택 응답을 받은 뒤 수정한다. 이전 진행 승인이나 일반 대화로 대신하지 않는다.
8. **검수 기준 확립**: 응답으로 확인된 피드백 내용 자체를 이번 수정의 절대 기준으로 잠근다. 각 항목에 ID를 붙이고 빠뜨리지 않는다. 사용자 유지 조건도 그대로 지킨다. AI가 임의 기준을 더하거나 조건을 낮추지 않는다.
9. **수정 진행**: 같은 명세·피드백·검수 항목으로 담당에게 수정 지시한다. 자동 재시도도 승인된 수정 범위와 작업별 모델·호출 허용량을 넘지 않는다.
10. **자체 검수**: 수정본을 사용자에게 보여주기 전에 확정된 모든 항목과 실제 결과물을 하나씩 대조하고 파일 버전·항목별 근거를 기록한다. 확인하지 못한 항목·부분 충족·경고·실패는 통과가 아니다.
11. **합격 후 보고**: 확정 기준을 **전부 통과한 수정본만** 사용자에게 보고한다. 불합격은 9단계로 돌아간다. 자체 합격을 사용자 합격으로 표시하지 않는다. 기준 충족을 검증할 수 없거나 허용된 제작 범위가 소진되면 완료로 꾸미지 않고 제한을 알린다.
12. **최종 판정**: 사용자 검토로 추가 피드백이 오면 6단계로 돌아간다. 실제 사용자 합격 판정이 있어야 완료한다. 게임 반영·Git 저장은 별도의 승인 범위를 유지한다.

`pipeline`에는 현재 단계, 최초/수정 구분, 피드백 묶음과 검수 근거를 기록한다. `stages`의 4가지 상태와는 별도다. 예전 작업에 수행하지 않은 단계를 소급 기입하지 않는다. 새 후속 작업부터 실제 브리핑·선택 응답·대면·피드백의 근거로 진행한다.

## 1. 단일 명세와 직접 전달

- 활성 총괄은 MAIN01이다. 사용자는 방향·재생 속도·최종 합격을 결정한다. MAIN01도 분석·시안 제작을 수행할 수 있다.
- 각 작업의 `통합작업명세.json` 한 파일에 최초 원문, 추가 정정, 최신 조건, 수량·각도, 유지/변경 범위, 참조 원본, 허용 파일, 모델 허가, 전문 프롬프트, 완료 기준을 기록한다. 별도 요청확인·전문프롬프트 파일을 편집 원본으로 병행하지 않는다.
- 정정은 원문을 삭제하지 않고 이력에 추가한다. 최신 조건과 과거 조건을 구분하고, 충돌이 해결되지 않으면 발송하지 않는다. 명세 변경 시 차수와 해시를 바꾸고 이전 승인을 무효화한다.
- 전문 프롬프트는 명세의 `current.professionalPrompt`에 작성한다. 각 요구사항 ID에 대응하는 적용 내용을 기록한다. 번역·구체화 과정에서 포즈·장비·모델·수량·동작 순서를 임의로 더하거나 바꾸지 않는다. 원문에 없는 가정은 제안으로 표시한다.
- 전달 경로는 `MAIN01 → 실제 제작 담당 → MAIN01`이다. 세계관은 자료 색인이며 전달·승인 노드가 아니다. 팀장이 직접 수행하거나 실제 전문 작업이 필요한 경우에만 하위 담당을 사용한다. 단순 전달·요약을 위한 AI 경유를 만들지 않는다.
- 하위 담당과 외주도 같은 명세·차수·해시를 사용한다. 실행에 사용한 실제 프롬프트와 명세의 프롬프트를 대조한다. 추가 해석이 필요하면 먼저 MAIN01에 돌린다.

## 2. 지정 문구로 진행 응답 구분 — 최신 사용자 지시

- 사용자가 나누어 설명하는 동안은 수합한다. 마지막 발화만 강조해 발송하거나 제작하지 않는다.
- 상세 브리핑 후 “진행할까요?” 질문에 **`################진행############` / `보류`** 선택지를 제공한다. 직접 입력란은 네이티브 질문 도구의 기본 입력란을 사용한다.
- 현재 확인 질문에 대해 사용자 답변이 지정 문구와 정확히 일치하면 진행 승인이다. 사용자가 그 문구를 직접 입력해 응답한 경우도 같다. 물리적인 클릭 출처를 따로 인증하지 않는다.
- 일반 채팅의 “진행”, “진행해”, “ㅇㅇ”, 사전 선택·침묵·시간 경과·다른 창 이동은 승인으로 처리하지 않는다. 지정 문구가 설명·예시·인용 속에 포함된 경우도 승인으로 처리하지 않는다. 이번 지정 방식 설명 자체는 제작 승인이 아니다.
- 실제 사용자 응답을 질문 ID·작업 ID·명세 해시·차수에 연결한다. AI가 대신 답하거나 사용자 응답을 만들어 기록하지 않는다. 응답 기록은 실제 대화 근거이며, 별도 사용자 인증 시스템이라고 보고하지 않는다.
- 작업대장은 현재 응답의 문구·대상·버전을 검사한다. 네이티브 클릭 인증 어댑터 부재를 이유로 막던 이전 차단은 제거한다. 확인 후 범위가 바뀌면 새 질문을 제공하고 이전 응답을 재사용하지 않는다.
- 이미 착수한 기존 승인 범위는 이 설정 때문에 복제·재호출하지 않는다. 새 확인 질문부터 지정 문구를 사용한다. 이 선택지 형식 변경은 사용자의 직접 지시로 반영한다.

## 3. 필독·착수·외주

- 매 새 작업에 자기 AGENTS, 이 규칙, 자기 작업진행방법, 분야 규정, 해당 통합 명세 및 필요한 작품 기준의 본문을 읽는다. 전체 작업대장·전체 조직도·관련 없는 작품 기록을 매번 첨부하지 않는다.
- `read-pack`은 해당 역할과 작업의 본문만 제공한다. 실제 읽은 문서별 적용 요약과 해시를 기록하고 `start`를 통과한 뒤 편집·생성한다. 목록만 읽거나 해시만 복사하는 것으로 대체하지 않는다.
- 제작팀과 독립 테스터를 분리한다. 테스터는 검사한 버전·재현·결과·제한을 보고하고 사용자 미적 합격을 대신하지 않는다.
- GPT Image 2.6은 일괄 금지하지 않는다. **해당 작업에 대한 명시적 사용 허가**를 통합 명세에 기록하고 그 모델·수량·범위만 호출한다. 키·크레딧·다른 작업 허가로 확대하지 않는다. 이번 운영 개편은 이미지 생성 허가가 아니다.
- 외주 완성 원본을 보존한다. 불필요한 분해·재조립·재생성은 하지 않는다. 필요한 가공은 명세 범위에서만 수행한다. 비밀키는 명세·소스·채팅에 기록하지 않는다.
- 새 Codex 담당의 기본값은 `gpt-6.1-sol / medium`. 별도 사용자 지시가 우선한다. 기존 실행을 중단해 모델을 바꾸지 않는다.

## 4. 네 가지 독립 상태

|표시|기록 내용|판정 근거|
|---|---|---|
|제작 완료|미착수·진행·완료·일부·실패·미확인|실제 산출물과 반환 증거|
|기술 검증|미검증·진행·통과·경고 포함 통과·실패·미확인|검사 대상 버전 및 결과|
|사용자 합격|미판정·합격·불합격·미확인|사용자 실제 판정 원문|
|게임 반영|미반영·반영·미확인|실제 적용 파일/버전 및 검증|

작업대장의 `stages`가 기준이다. 한 단계로 다른 단계를 추정하지 않는다. 과거 자료가 부족하면 미확인으로 남긴다. 발송 흐름(수합/버튼 승인 대기/발송/진행/반환)은 별도 `status`에 기록한다. 포괄적인 “사용자 대기” 상태를 사용하지 않는다.

## 5. 대화 보호와 보고

- 요청 수합·조건 수정·버튼 승인 대기 중에는 현재 주제를 활성 상태로 유지한다.
- 타 작업의 완료 회신은 수신·기록하되 `상태/완료알림큐.json`에 보관한다. 수정본은 10단계 자체 검수를 전부 통과해야 보고 가능한 큐에 넣는다. 시스템 wake나 worker_done만으로 대화에 완료 안내를 끼워 넣지 않는다.
- 현재 주제가 끝났음을 확인한 뒤 큐를 한 번에 읽어 보고한다. 무응답·경과 시간만으로 주제를 종료하지 않는다. 실제 보고 후에만 보고 완료로 표시한다. 앱 자체의 시스템 알림을 끄는 기능과는 구분한다.
- 결과 보고는 번호/실제 상태/작업명부터 시작한다. 이번에 설명하는 완료 항목은 초록 표시(미지원이면 🟢)를 사용한다. 제작·검증·합격·반영과 근거를 구분한다. 사용자가 단답을 요구하면 짧게 답한다.

## 6. 보존과 저장

- 같은 파일의 동시 편집을 피한다. 기존 원본·미커밋 작업·사용자 승인/반려·실제 송수신 증거를 보존한다. 운영 정리가 기존 작품의 재승인을 뜻하지 않는다.
- 오래된 운영 본문은 활성 규정에서 제거하고 복구용 사본으로만 보관한다. 과거 요청의 실제 모델 제한·판정·작업 ID를 거짓으로 고치지 않는다.
- Git 저장은 사용자 요청 때만 `작업기록 → 검증 → 커밋 → 업로드 → 원격 해시 확인` 순서로 한다. 자동 커밋·푸시를 하지 않는다. 로컬 산출물·운영 기록 작성은 GitHub 저장과 다르다.
