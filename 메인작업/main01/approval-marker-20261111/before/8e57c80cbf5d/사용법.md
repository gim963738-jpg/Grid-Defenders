# MAIN01 작업대장 v4 — 12단계

운영 원본은 [운영규칙](../운영규칙.md), 작업 지시는 `작업/<ID>/통합작업명세.json` 하나다. 상태·근거·현재 12단계는 task.json에 연결한다. 명령 앞에 `python 작업관리/도구/작업대장.py`를 붙인다.

|단계|실행 및 기록|
|---|---|
|1 요청 수신|`new --main main01 --branch <역할> --title <제목> --request-file <원문>`|
|2 상세 브리핑|현재 조건을 `update-spec --task <ID> --file <현재조건.json> --correction <원문> --source <실제출처>`로 정리. 아주 상세하고 쉬운 설명을 사용자에게 제시하고 `pipeline --action brief --task <ID> --evidence <브리핑근거.json>` 기록|
|3 진행 버튼 대기|`approval-request --task <ID>`의 질문·차수·해시로 실제 시스템 진행 버튼을 제공. 인증된 클릭만 confirm 허용|
|4 전문 프롬프트 발송|`prepare` 후 공식 도구로 같은 명세 전달. 실제 영수증으로 `record --action sent`. 담당 read-pack → 읽기확인 → start 후 제작|
|5 최초 결과 대면|실제 반환 근거로 `record --action returned`. 기본은 자체 미적 선별 없이 사용자에게 먼저 보여주고 `pipeline --action present` 기록|
|6 피드백 수신|`pipeline --action feedback --evidence <사용자피드백.json>` 또는 `record --action revise --quote <사용자원문> --evidence <실제출처>`. 여러 발화를 같은 피드백 묶음에 누적|
|7 피드백 확인 버튼|수정 전문 프롬프트를 update-spec으로 준비. approval-request가 `피드백 받음(적용)` 버튼을 요구. 일반 진행 버튼·문자 확인으로 대체 불가|
|8 검수 기준 확립|피드백 클릭 confirm 후 `pipeline --action criteria --evidence <확정근거>`로 원문 항목을 그대로 잠금|
|9 수정|같은 명세·확정 기준으로 prepare → 실제 발송/영수증 → 필독/start → 수정|
|10 자체 검수|returned 후 `pipeline --action self-review --evidence <검수.json>`. 모든 피드백 항목과 실제 결과 대조. 누락·불명확·부분 충족·경고는 통과 아님|
|11 합격본 보고|전 항목 pass만 보고 큐에 들어감. 사용자에게 보여준 뒤 pipeline present. 실패는 9단계로 돌아가 같은 승인 범위에서 수정|
|12 최종 판정|실제 사용자 원문으로 `record --action accept --quote <판정> --evidence <출처>` 후 완료. 추가 피드백은 6단계로 복귀|

모든 작업 명령은 `--task <ID>`와 필요시 `--main main01`을 사용한다. record/start/stage/pipeline은 `--evidence <실제파일>`이 필요하다. prepare는 실제 송신이 아니다.

현재 **네이티브 버튼 클릭 인증 어댑터가 미연결**이므로 3·7단계의 confirm과 이후 발송은 차단된다. 선택 질문 표시는 가능하지만 클릭과 자유 입력을 인증하는 이벤트가 필요하다. 로컬 JSON, 인용문, AI 클릭, gate-resolve로 우회하지 않는다. 테스트의 가짜 클릭 리더는 임시 검사 전용이다.

통합 명세의 current: goal,deliverables,requirements[{id,text,source}],keep,change,references,allowedFiles,checks,professionalPrompt,promptCoverage{요구ID:프롬프트구절},image26{allowed,userEvidence},unresolved. 수정 차수는 feedbackCoverage{피드백ID:프롬프트구절}로 모든 피드백을 실제 수정 프롬프트에 연결한다. 입력용 JSON을 별도의 지시 원본으로 유지하지 않는다.

브리핑 JSON: goal,inputs,deliverables,keep,change,sequence,checks,unknowns에 사용자에게 실제 설명한 상세 내용을 문자열로 기록한다. 자동 문자열 검사는 설명의 의미나 실제 사용자 이해를 증명하지 않는다. 사용자 제시 근거를 정직하게 연결한다.

피드백 JSON: `{ "text": "사용자 실제 피드백" }`. 원문은 Single Spec의 feedback.items에 누적되고 항목 ID가 붙는다. 버튼 질문 후 새 피드백이 오면 이전 선택을 무효화하고 다시 수합한다. criteria 명령은 내용을 새로 쓰지 않고 그 원문을 잠근다.

검수 JSON: task,iteration,specSha256,resultEvidence(현재 pipeline.lastResult),artifacts[{path,sha256}],checks[{id,status,note,evidence:{path,sha256}}]. 모든 확정 항목의 실제 대조 근거가 필요하다. 전부 pass일 때만 11단계. 검수 뒤 명세·결과·근거 파일이 바뀌면 보고를 차단한다. 코드가 미적 품질을 자동 판독하는 기능은 아니며 MAIN01의 실제 이미지·동작 검수가 필요하다.

GC9 같은 1차 예외는 current.firstReviewPreset에 사전에 확립된 establishedEvidence{path,sha256}와 criteria[{id,text}]가 있을 때만 적용한다. 제작 전 사용자에게 제시하는 명세에 포함해야 하며 반환 후 임의로 추가할 수 없다. 기본 최초 결과는 self-review 단계로 보내지 않는다.

작품별 추가 기준은 초안에서 set-readings로 연결한다. read-pack은 역할 필독과 현재 원문·정정·브리핑·피드백·조건만 보여준다. 과거 버전은 같은 파일에서 필요할 때 읽는다. 읽기 확인 JSON에는 task,iteration,role,workSummary,documents[{path,sha256,applies}],requirementCoverage{요구ID/피드백ID:적용내용}를 넣고 start한다.

4단계 stages는 계속 독립 관리한다: production(제작 완료),technical(기술 검증),user(사용자 합격),integration(게임 반영). 자체 검수 통과는 사용자 합격이 아니다. 실제 합격 뒤 승인된 게임 적용 근거가 있어야 integrated를 기록한다. Git 저장은 별도 사용자 요청 때만 한다.

대화 시작은 `topic --name <주제>`, 실제 주제 종료는 동일 이름과 `--close`. 타 작업 완료는 큐로 미루고 종료 후 notifications로 일괄 확인한다. 실제 보고 후 `notifications --reported <eventID...>`. 현재 차수에서 보고 가능한 최초본/자체합격본만 반환하며 오래된 알림이나 검수 실패본을 끼워 넣지 않는다.

기존 작업의 수행하지 않은 단계를 소급하지 않는다. 과거 상태와 판정은 보존하고 새 후속 제작은 update-spec 및 실제 브리핑부터 시작한다. list는 pipeline과 독립 4단계를 함께 표시한다. 직접 파일 편집이나 도구 밖의 실행을 OS 수준에서 차단하는 보안 기능은 아니므로 모든 담당이 같은 절차를 지켜야 한다.

검사: `python -m unittest discover -s 작업관리/도구 -p "test_*.py" -v`. 실제 클릭 연동과 모의 이벤트 검사를 구분한다. 구형 초기화 스크립트는 재실행하지 않는다.
