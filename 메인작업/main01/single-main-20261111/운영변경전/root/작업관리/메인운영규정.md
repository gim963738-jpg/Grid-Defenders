# 메인 운영 규정 — OPS-004

## 기본 모델·추론 강도 (OPS-005, 2026-11-09)

사용자 요청으로 다음 작업의 기본값은 **GPT-6.1 Sol (`gpt-6.1-sol`) / 중간 (`medium`)**이다. 새 Codex 담당을 실행할 때 지원되는 공식 실행 옵션에 `--model gpt-6.1-sol --effort medium`을 명시한다. 메인·팀장·하위 담당 모두 같은 기본값을 따른다. 별도 모델을 사용하도록 사용자가 지시한 작업은 그 지시를 우선하고 작업이 끝난 뒤 다음 작업에는 이 기본값을 사용한다. 이미지/영상 외주 모델 설정을 이 텍스트 모델로 바꾸지 않는다.

규정 기록과 실제 앱 선택은 구분한다. 기존 Orca 대화에 명시된 모델·강도는 기본값과 다를 수 있으므로 다음 작업 전 실제 표시/실행 옵션을 확인한다. 실행 중인 턴을 재시작하거나 중단해서 모델을 바꾸지 않는다.

공통 기준: [규정 A](규정A.md). 담당 메인은 메인01·02·03 중 요청을 받은 창이다. 모든 메인은 분석·기획·시안 제작과 지시·검수를 수행할 수 있다.

## 실제 작업 흐름

요청 수신 → 기존 기준 확인 → 필요 시 메인에서 실제 시안 제시 → 사용자 선택 → 조합 시안·이해 내용 제시 → 사용자 확인 기록 → 전문 프롬프트 준비 → 담당 브랜치에 전달 → 담당의 작업 방법·작품 기준 필독 및 착수 기록 → 결과·검증 수신 → 사용자 판정 → 기준 보완·수정 지시의 이해 재확인 → 재작업 또는 통합.

예: 인터페이스10종 요청은 실제 시안10종을 제시한다. 'UI4번·필드6번'을 선택하면 해당 조합을 보여주고 확인받은 후 구현 지시한다. 이 예시는 현재 발송할 제작 작업이 아니다.

## 공통 파일과 로컬 작업

이 저장소의 `작업관리/`가 공유 원본이다. 다른 메인의 로컬 체크아웃을 최신 게임·규정의 사본으로 가정하지 않는다. 각 창의 `작업연결.json`에서 공유 원본을 찾고 [메인목록](메인목록.json), [브랜치목록](브랜치목록.json), [작업대장](작업대장.md)을 읽는다. 채팅 내용 전체가 자동 공유되는 대신 확인 내용·판정·진행 상태를 공유 문서로 연결한다.

시안·비교 자료는 각 메인의 `메인작업/<main-id>/`에 보관하고 작업대장에 실제 경로를 연결한다. 분야별 실제 제작은 해당 작업 공간으로 보낸다. 현재 UI 구현의 작업 사본은 브랜치목록의 ui 경로다. root의 이전 미커밋 구현은 보존 중인 기준 사본이며 새로운 UI 편집 대상은 UI 전용 공간이다.

UI 새 작업의 시작 사본은 `기록/OPS-001/ui-copy-manifest.json`과 대조한다. 기존 미커밋 변경과 새 작업의 변경을 구분하고 승인된 새 변경만 통합한다. 인계한 기존 UI 시안7파일은 참고 이력이며 사용자 선택·합격으로 새로 승격하지 않는다.

## 작업대장 도구

공유 원본에서 `python 작업관리/도구/작업대장.py --help`를 사용한다. 다른 메인에서는 공유 원본의 절대 도구 경로를 호출한다. `new → set-readings → confirm → prepare → record sent → read-pack → start → 작업 → record returned → record accept 또는 revise` 순서이며 수정 차수도 새 필독 확인을 수행한다. 작품별 추가 기준이 없는 경우 set-readings는 생략하되 전문 지시에 기준 근거를 명시한다.

`confirm`에는 사용자의 실제 확인 원문과 대화/파일 근거를 기록한다. AI가 사용자 확인을 만들어 입력하면 안 된다. 이해문·전문 프롬프트·규정이 확인 후 달라지면 prepare가 차단된다. prepare는 발송 준비와 잠금이며 실제 송신을 뜻하지 않는다.

## 실제 전달과 회신

새로운 감독 작업은 `orca orchestration worker-start --spec-file <발송준비의 prompt가 가리키는 필독 첨부 발송지시> --worktree <브랜치목록의 selector> ...`를 사용한다. 기존 담당 세션이 있으면 현재 상태·소유권을 먼저 확인하고 같은 담당의 공식 메일박스/Dispatch로 이어 보낸다. 진행 중인 편집자를 복제하지 않는다. 정확한 실행 옵션과 lifecycle은 설치된 `orca skills get orchestration`의 버전별 가이드를 따른다.

첫 발송 후 Task·Dispatch·Run 또는 세션 핸들 및 CLI 영수증을 작업에 기록한다. Orca 감독 작업을 시작했다면 worker-start의 next를 따르고 턴을 끝내 회신을 받는다. 폴링 스크립트·터미널 입력으로 감독 흐름을 우회하지 않는다. 반환 시 작업번호·수정 차수·담당 메인·결과 경로를 명시한다. 메인은 결과 근거를 검토하고 누락·모순이 있을 때 필요한 검사를 추가한다.

## 3개 메인의 충돌 방지

각 작업은 하나의 담당 메인이 소유한다. 다른 메인으로 이동할 때 인계를 기록한다. 도구는 전역 기록 갱신을 짧게 잠그고, 발송 준비 시 대상 브랜치의 작업 잠금을 확인한다. 같은 브랜치로 겹친 준비를 차단한다. 실제 중단·반환을 확인하기 전에 시간 초과만으로 잠금을 해제하지 않는다. 현재 폴더는 운영 준비이며 승인된 실제 제작 작업은 아직0건이다.

## Windows 실행 메모

이번 준비의 마지막 확인에서 새 Windows PowerShell 프로세스 시작 오류0x800705af를 관찰했고, cmd.exe에서 Python 검증 스크립트를 실행해 최종 대조를 완료했다. 같은 오류가 나면 cmd.exe 또는 이미 열려 있는 사용 가능한 셸을 사용한다. 여러 줄 코드는 파일로 저장해 호출하며 다른 프로젝트 프로세스 종료나 OS 설정 변경을 임의로 하지 않는다. 이 메모는 실제 관찰한 도구 실행 경로이며 모든 PowerShell 실행이 복구되었다는 뜻은 아니다.

## OPS-002 도메인 기준 작업 분류

메인3개는 [세계관 트리](도메인/트리.json)에서 요청의 기획 소속을 확인한다. 몬스터 디자인과 몬스터 스프라이트, 캐릭터 공통 설정과 일러스트·스프라이트·능력치·스킬을 각각 연결한다. 기존 역할 ID는 유지하며 index.json의 실제 소스 위치·자료 상태와 selector를 사용한다. 부모 소속이 같아도 제작·검수 기준은 각 분야 규정을 따른다. 새로운 공간에 들어 있는 과거 Git 사본을 최신 데이터로 가정하지 않는다.


## OPS-003 팀장 체계 적용 — 2026-11-09

현재 조직은 [조직.json](조직.json), 운영은 [팀장운영규정.md](팀장운영규정.md), 공유 파일 책임은 [파일담당표.md](파일담당표.md)를 따른다. 기존 5담당을 팀장으로 이어받고 게임개발 팀장·독립 테스터를 신설한다. 총 6개 팀장과 독립 테스터이며 메인3개 역할을 유지한다. 자료의 세계관 계층과 원본 위치는 보존한다. 실제 조직 관계는 조직.json이 우선한다. 원본 완성 시트의 불필요한 분해·재조립은 기본 공정에서 제외한다. 사용자 확인 근거는 OPS-003 대화기록이며 새 게임 콘텐츠 지시0건이다.


## OPS-004 매 작업 하달 후 필독 — 2026-11-09

사용자 요청으로 모든 역할의 작업진행방법.md와 requiredReadings를 연결했다. 작업을 받은 에이전트는 본문 읽기 → 작업별 적용 요약 → start 착수 확인 후 작업한다. 전문지시와 하위위임에 실제 필독 경로/버전을 포함하며, 목록만 복사하거나 과거 초기화 응답으로 대신하지 않는다. read-pack/start 절차는 [작업대장 사용법](도구/사용법.md)을 따른다. 사용자 추가 승인 절차가 아니다.
