# 메인 결과 보고 형식 — v1.1 / 2026-11-09

사용자 직접 요청: “나한테 결과물 보낼때 1. 진행중 2.초록글씨로 완료된 내용 지금 설명하는 주제 3.진행중 이런식으로 먼저 시작하고 내용을 전달해줘 여러개 보내보니까 정리가 안된다 메인 02.03한테도 이내용 전달해”.

메인01/02/03 모두 적용한다. 결과 보고와 의미 있는 진행 보고는 다음 순서를 따른다.

1. 본문 전에 현재 담당 작업 묶음을 번호 목록으로 먼저 표시한다. 각 줄은 `상태 — 실제 작업명`으로 쓴다. 개수는 실제 작업 수에 맞춘다. ‘진행 중’만 적어 무엇인지 알 수 없게 하지 않는다.
2. **이번 본문에서 설명할 완료된 항목**은 초록 글씨로 표시하고 `완료`와 작업명을 명시한다. 필요하면 `이번 보고`를 붙인다. 다른 작업은 현재 상태로 유지한다.
3. 목록 다음에 이번 항목의 결과·확인 근거·열 수 있는 링크·남은 과제를 설명한다. 여러 작업 결과를 상태 목록 없이 섞어 보내지 않는다.
4. 진행 중/검증 중/사용자 평가 대기/보류/막힘을 실제 상태대로 표시한다. 현재 설명한다는 이유만으로 미완료를 완료로 바꾸지 않는다. 제작 완료와 기술검증/사용자합격/게임반영을 구분한다.
5. 작업명/번호는 한 보고 안에서 일관되게 쓰고, 다른 메인의 작업을 자신의 완료로 표시하지 않는다. 사용자가 여러 메인을 함께 볼 수 있게 책임 메인이 필요하면 함께 표시한다.

예시:

```text
1. 진행 중 — UI 시안 제작
2. 완료 — 몬스터 3종·9방향 이미지 (이번 보고: 초록 글씨)
3. 검증 중 — 이미지 대조 도구

몬스터 이미지 결과와 링크, 검수 내용, 남은 평가를 설명한다.
```

색상 표현은 실제 채팅 렌더러의 지원 범위를 확인한다. Orca의 `ORCA_CHAT_SCRATCH_DIR`가 제공되면 orca-chat-visuals 스킬의 HTML 시각화로 번호 목록과 완료 줄에 초록색 글씨를 적용할 수 있다. 사용자 창/탭/패널을 조작하지 않는다. HTML span/style이 채팅에서 처리되지 않는데 초록 글씨가 적용됐다고 주장하지 않는다. 색상을 지원하지 않는 환경에서는 최소한 `🟢 완료 — 작업명 (이번 보고)`로 구분하고 상태/작업명을 유지한다.

공유 원본은 이 파일이다. 각 메인의 AGENTS 및 작업진행방법에서 연결한다. 메인 보고 양식 변경이므로 진행 중인 제작 담당의 공통 운영 규정/작품 기준은 수정하지 않는다.

## 확인 대기 작업의 선택 버튼 — v1.1

사용자 추가 요청: “내가 지시하고 허락받는도중 다른채팅으로 넘어간것도 … 버튼눌러서 진행 바로 할수있게끔 조치”.

1. 실제로 사용자 확인이 필요한 작업은 번호 목록에 `확인 대기 — 작업명`으로 표시한다. 그 작업의 이해 내용·유지/변경 범위·결과물·완료 기준을 짧게 설명한 뒤, 사용 가능한 네이티브 질문 도구로 `이 내용으로 진행` / `수정 요청` 선택 버튼을 제공한다. 예: `functions.request_user_input_async`. 단순 보고나 이미 승인된 범위에 확인 질문을 새로 만들지 않는다.
2. 질문 제목에 작업명과 작업번호/수정 차수를 넣어 어떤 지시에 대한 답인지 식별한다. 선택 버튼은 실제 사용자 제출을 받아야 한다. 사전 선택·침묵·다른 채팅으로 이동·시간 경과는 승인이 아니다. 자유 입력 피드백도 같은 작업에 연결한다.
3. 사용자 확인을 기다리는 요청·차수·이해 내용을 기존 작업 기록에 보존한다. 사용자가 돌아오면 대기 중인 정확한 범위를 이어서 처리하고 같은 허락을 다시 받지 않는다. 다른 작업/변경된 차수에 과거 버튼 응답을 재사용하지 않는다. `수정 요청`은 수정 내용 확인 단계이며 임의 수정 제작의 승인이 아니다.
4. 승인 답변이 도착하면 담당 메인이 원문과 대상 작업을 기록하고 기존 전문 지시·필독·송신 절차로 진행한다. 다른 메인 소유 작업은 실제 담당에게 인계하며 중복 발송하지 않는다.
5. 채팅 HTML 시각화에 작동하지 않는 진행 버튼을 그리지 않는다. 네이티브 질문 도구가 없다면 공식 앱의 지원 기능을 확인하고, 지원하지 않는 환경에는 그 사실과 텍스트 답변 방법을 안내한다. 앱을 수정하거나 창·탭·패널을 조작하지 않는다.
6. 이 규칙은 앞으로의 확인 질문을 선택형으로 제공하는 설정이다. 이미 보낸 일반 텍스트 메시지에 버튼을 소급 부착했다거나 다른 채팅으로 이동한 뒤에도 앱이 버튼을 보존하는 동작을 실제 검사 없이 검증 완료로 보고하지 않는다.

변경 근거: 2026-11-09 사용자 직접 요청. v1.0의 상태 목록·초록 강조 규칙을 유지하고 확인 대기 응답 방식만 추가했다.

## 총괄 3메인의 절차 확인·마지막 행동 안내 — v1.2 / 2026-11-09

사용자 직접 요청으로 main01/02/03 모두 같은 기본값을 적용한다. 사용자가 “이렇게 해야겠다/이렇게 진행해야겠다”라고 방향을 설명해도 곧바로 제작 하달로 건너뛰지 않는다.

1. 요청의 이해·범위와 실제 진행 승인 여부를 구분한다. 해당 규정 본문, 최신 판정, 사전확인, 담당·동시 편집 충돌을 확인하고 그 근거를 작업 기록에 남긴다. 마지막 멘트만 붙이는 것으로 이 절차를 대신하지 않는다.
2. 작업 방향 정리나 실행 안내를 마칠 때 마지막 문장에 다음 행동과 승인 상태를 명확히 표시한다. **승인된 범위**는 “절차를 확인한 뒤 담당 팀장에게 작업을 하달하겠습니다.”, **진행 승인 전**은 “진행 승인 대기 상태이며, 승인 후 절차를 확인하고 작업을 하달하겠습니다.”를 기본 표현으로 사용한다. 메인이 직접 수행하는 승인된 업무는 “절차를 확인한 뒤 진행하겠습니다.”로 안내한다.
3. 이미 하달했다면 미래형으로 되돌리지 말고 “절차 확인 후 작업을 하달했으며, 착수·검수 절차도 확인하겠습니다.”처럼 실제 상태를 표시한다. 완료·대기·보류 보고도 실제 다음 행동에 맞춰 끝맺는다. 질문만 하는 대화 등에 실행을 약속하는 상투 문구를 붙이지 않는다.
4. 공식 발송영수증과 담당의 현재 차수 필독/착수 확인까지 연결한다. 계획을 실제 하달로, 공지 발송을 상대의 읽기 완료로 표시하지 않는다.
5. 이 설정은 신규 제작의 포괄 승인이나 진행 전 대기 규칙의 폐지가 아니다. 같은 범위의 실제 승인에는 허락을 반복 요청하지 않는다. 저장 요청 전 커밋·푸시 금지도 유지한다.
