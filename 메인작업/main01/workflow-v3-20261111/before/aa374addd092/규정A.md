# 공통 작업 규정 A — v2.2.0

상태: 사용자가 대화에서 확정한 새 운영 방식. 예시 슬라임·디자인10종은 실제 제작 지시가 아니다.

## 역할과 확인

1. 활성 메인은 main01 한 곳이며 요청·분석·기획·실제 시안 제작·비교·선택 지원·지시·검수를 담당한다. 메인을 지시만 하는 창으로 제한하지 않는다.
2. 사용자가 요구한 수의 실제 비교 시안을 제시하고 번호를 붙인다. UI4번+필드6번 같은 부분 선택은 통합 시안으로 보여준다. 미확정 요소를 선택된 것으로 간주하지 않는다.
3. **최초 제작 지시와 모든 수정 지시를 보내기 전에**, 메인이 이해한 목표·참조·유지/변경 요소·범위·완료 기준을 사용자에게 제시하고 이해가 맞다는 실제 확인을 받는다. 침묵·대기 시간·AI 자체 판단·과거 다른 작업의 승인은 확인이 아니다.
4. 담당 브랜치는 확인된 전문 지시를 수행하며 기존 규정을 읽고 결과물과 검증, 기준 보완 내용을 함께 제출한다. 실제 작업은 자기 작업 공간에서 한다.

## 시작 순서와 기존 기준

규칙 → 현재 작업 목록 → 해당 분야 기존 규정·최신 사용자 판정 → 직전 작업 기록 → 실제 파일을 읽는다. 대상 파일·수정 범위·제외 범위·완료 조건·검증 방법을 사전에 보고하고 사전확인 문서를 저장한 뒤 수정한다. 사용자 확인이 이미 해당 범위에 있으면 같은 허락을 반복해서 요구하지 않는다.

[기존 개발규칙](../문서/00_개발규칙/개발규칙.md), 각 작업 공간 AGENTS.md, [분야별 기준](기준/README.md)을 함께 적용한다. 최신 사용자 요청을 우선한다. 오래된 문서나 특정 작품의 프레임 수·판정·색상을 전 분야의 새 기준으로 복제하지 않는다. 충돌과 미확정 조건은 메인에 보고해 사용자에게 확인한다.

## 전문 지시와 제출

전문 지시에는 작업번호·원래 요청·이해 확인 근거·담당 메인·담당 브랜치·적용 규정과 버전·원본 참조 경로·유지 사항·변경 사항·허용/제외 파일·산출물 형식·검증 방법·회신 경로를 포함한다. '다른 창의 대화를 보라'는 지시만 보내지 않는다.

각 작업은5종 기록(대화기록·사전확인·작업일지·정의문서·버전관리)을 유지한다. 사전 문서를 작업 후 작성해 사전 기록이라고 보고하지 않는다. 결과물 제작 완료·기술 검증 완료·사용자 합격·통합·커밋·푸시를 구분한다. 로컬 저장을 원격 저장으로 보고하지 않는다.

## 피드백으로 기준 정교화

반려 시 사용자 원문, 관찰한 문제, 유지할 장점, 수정 범위, 재검수 기준을 연결한다. 담당 AI는 결과물 수정과 함께 재발을 막을 기준 변경안을 제출한다. 사용자 확인으로 확정된 기준만 활성 규정에 반영하고 AI 추정·제안은 별도 표시한다. 기준의 버전·변경 이유·근거 작업번호와 전후 결과를 남긴다. 실패·미검증 이미지를 승인 참조로 승격하지 않는다.

## 병행 작업과 통합

공유 작업대장의 작업번호·담당 메인·브랜치·수정 차수로 작업을 구분한다. 독립 작업은 병행한다. 같은 브랜치/공통 파일에 동시 편집을 지시하지 않는다. 충돌하면 대기 또는 별도 작업 공간을 사용한다. 잠금은 시간 경과만으로 빼앗지 않는다.

사용자 합격 후 승인된 범위만 통합한다. 진행 중인 원본·미커밋 변경·기존 기준·이전 결과를 보존한다. 합격이 자동 커밋·푸시를 뜻하지 않는다. 실제 송신은 Orca 작업 위임 도구를 사용하고 영수증·Task/Dispatch 또는 세션 핸들을 기록한다. 무응답을 실패나 미전달로 단정해 중복 송신하지 않는다.

## 변경 관리

공통 규정은 이 파일 하나를 기준으로 한다. 분야 규정은 각 분야 기존 기준을 연결하며 세 메인이 작업마다 최신판을 읽는다. 각 메인은 자기 작업 기록을 갱신하고 공통 규정 변경은 단독으로 확정하지 않는다. 새 시안·통합 시안·실제 구현은 모두 사용자 판정 대기 상태로 제출할 수 있다.

## 세계관 중심 도메인 계층 (OPS-002)

사용자 요청으로 [세계관 도메인 트리](도메인/README.md)를 적용한다. 세계관 아래 몬스터와 캐릭터를 두고 몬스터 스프라이트, 캐릭터 일러스트·스프라이트·능력치·스킬을 각 세부 담당으로 연결한다. 기획 소속과 제작 공정을 구분하며, 몬스터와 캐릭터의 신체 구조·동작·검수 기준을 합치지 않는다.

새 작업마다 도메인 트리의 역할 ID와 index.json에서 담당 작업 공간·원본 위치·자료 상태를 확인한다. 작업 목록의 Nesting은 Git 병합이나 원본 파일 이동을 뜻하지 않는다. 기존 역할 ID와 전문 규정·참조 원본·과거 판정을 보존한다. 실제 제작 지시의 사용자 이해 확인 절차는 그대로 적용한다.


## OPS-003 팀장 체계 적용 — 2026-11-09

현재 조직은 [조직.json](조직.json), 운영은 [팀장운영규정.md](팀장운영규정.md), 공유 파일 책임은 [파일담당표.md](파일담당표.md)를 따른다. 기존 5담당을 팀장으로 이어받고 게임개발 팀장·독립 테스터를 신설한다. 총 6개 팀장과 독립 테스터이며 메인3개 역할을 유지한다. 자료의 세계관 계층과 원본 위치는 보존한다. 실제 조직 관계는 조직.json이 우선한다. 원본 완성 시트의 불필요한 분해·재조립은 기본 공정에서 제외한다. 사용자 확인 근거는 OPS-003 대화기록이며 새 게임 콘텐츠 지시0건이다.


## OPS-004 매 작업 하달 후 필독 — 2026-11-09

사용자 요청으로 모든 역할의 작업진행방법.md와 requiredReadings를 연결했다. 작업을 받은 에이전트는 본문 읽기 → 작업별 적용 요약 → start 착수 확인 후 작업한다. 전문지시와 하위위임에 실제 필독 경로/버전을 포함하며, 목록만 복사하거나 과거 초기화 응답으로 대신하지 않는다. read-pack/start 절차는 [작업대장 사용법](도구/사용법.md)을 따른다. 사용자 추가 승인 절차가 아니다.
