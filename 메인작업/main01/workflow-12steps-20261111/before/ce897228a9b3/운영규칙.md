# MAIN01 운영 규칙 — v3.0 / 2026-11-11

근거: 사용자의 「MAIN01 운영 규칙 및 워크플로우 개편」 직접 지시. 이 파일이 현재 운영의 단일 원본이다. 과거 기록은 사실 확인용이며 현재 작업의 명령이 아니다.

## 1. 단일 명세와 직접 전달

- 활성 총괄은 MAIN01이다. 사용자는 방향·재생 속도·최종 합격을 결정한다. MAIN01도 분석·시안 제작을 수행할 수 있다.
- 각 작업의 `통합작업명세.json` 한 파일에 최초 원문, 추가 정정, 최신 조건, 수량·각도, 유지/변경 범위, 참조 원본, 허용 파일, 모델 허가, 전문 프롬프트, 완료 기준을 기록한다. 별도 요청확인·전문프롬프트 파일을 편집 원본으로 병행하지 않는다.
- 정정은 원문을 삭제하지 않고 이력에 추가한다. 최신 조건과 과거 조건을 구분하고, 충돌이 해결되지 않으면 발송하지 않는다. 명세 변경 시 차수와 해시를 바꾸고 이전 승인을 무효화한다.
- 전문 프롬프트는 명세의 `current.professionalPrompt`에 작성한다. 각 요구사항 ID에 대응하는 적용 내용을 기록한다. 번역·구체화 과정에서 포즈·장비·모델·수량·동작 순서를 임의로 더하거나 바꾸지 않는다. 원문에 없는 가정은 제안으로 표시한다.
- 전달 경로는 `MAIN01 → 실제 제작 담당 → MAIN01`이다. 세계관은 자료 색인이며 전달·승인 노드가 아니다. 팀장이 직접 수행하거나 실제 전문 작업이 필요한 경우에만 하위 담당을 사용한다. 단순 전달·요약을 위한 AI 경유를 만들지 않는다.
- 하위 담당과 외주도 같은 명세·차수·해시를 사용한다. 실행에 사용한 실제 프롬프트와 명세의 프롬프트를 대조한다. 추가 해석이 필요하면 먼저 MAIN01에 돌린다.

## 2. 버튼 승인 — 최우선

- 사용자가 나누어 설명하는 동안은 수합한다. 마지막 발화만 강조해 발송하거나 제작하지 않는다.
- 발송 직전 최신 명세의 결과물·수량·각도·유지/변경·제작 경로를 요약하고, 시스템 선택 질문 **“진행할까요?” / “진행”·“수정 요청”**을 제공한다.
- 일반 채팅의 “진행”, “진행해”, “ㅇㅇ”는 실행 승인이 아니다. 실제 사용자가 해당 명세·차수의 `진행` 버튼을 클릭한 사실이 확인되어야 한다. 사전 선택·침묵·시간 경과·다른 창 이동도 승인이 아니다.
- 버튼 사건은 질문 ID·작업 ID·명세 해시·차수·선택값·사용자 출처와 연결한다. AI가 작성한 근거 JSON, 인용문, `source=button` 자기 신고, 에이전트가 실행한 gate-resolve를 클릭 증거로 삼지 않는다.
- 현재 제공 도구는 선택 질문을 표시할 수 있지만 클릭과 자유 입력을 구별하는 신뢰할 수 있는 수신 이벤트를 확인하지 못했다. 따라서 작업대장 `confirm`/`prepare`는 검증 가능한 이벤트 연결 전까지 실행을 차단한다. 버튼 검증이 구현됐다고 보고하거나 텍스트 승인으로 우회하지 않는다.
- 이미 착수한 기존 승인 범위는 이 설정 때문에 복제·재호출하지 않는다. 새로운 발송·수정 범위에는 새 버튼 규칙을 적용한다. 이 운영 개편 자체는 사용자의 즉각 반영 직접 지시로 수행한다.

## 3. 필독·착수·외주

- 매 새 작업에 자기 AGENTS, 이 규칙, 자기 작업진행방법, 분야 규정, 해당 통합 명세 및 필요한 작품 기준의 본문을 읽는다. 전체 작업대장·전체 조직도·관련 없는 작품 기록을 매번 첨부하지 않는다.
- `read-pack`은 해당 역할과 작업의 본문만 제공한다. 실제 읽은 문서별 적용 요약과 해시를 기록하고 `start`를 통과한 뒤 편집·생성한다. 목록만 읽거나 해시만 복사하는 것으로 대체하지 않는다.
- 제작팀과 독립 테스터를 분리한다. 테스터는 검사한 버전·재현·결과·제한을 보고하고 사용자 미적 합격을 대신하지 않는다.
- GPT Image 2.6은 일괄 금지하지 않는다. **해당 작업에 대한 명시적 사용 허가**를 통합 명세에 기록하고 그 모델·수량·범위만 호출한다. 키·크레딧·다른 작업 허가로 확대하지 않는다. 이번 운영 개편은 이미지 생성 허가가 아니다.
- 외주 완성 원본을 보존한다. 불필요한 분해·재조립·재생성은 하지 않는다. 필요한 가공은 명세 범위에서만 수행한다. 비밀키는 명세·소스·채팅에 기록하지 않는다.
- 새 Codex 담당의 기본값은 `gpt-6.1-sol / medium`. 별도 사용자 지시가 우선한다. 기존 실행을 중단해 모델을 바꾸지 않는다.

## 4. 네 가지 독립 상태

|표시|기록 내용|판정 근거|
|---|---|---|
|제작 완료|미착수·진행·완료·일부·실패·미확인|실제 산출물과 반환 증거|
|기술 검증|미검증·진행·통과·경고 포함 통과·실패·미확인|검사 대상 버전 및 결과|
|사용자 합격|미판정·합격·불합격·미확인|사용자 실제 판정 원문|
|게임 반영|미반영·반영·미확인|실제 적용 파일/버전 및 검증|

작업대장의 `stages`가 기준이다. 한 단계로 다른 단계를 추정하지 않는다. 과거 자료가 부족하면 미확인으로 남긴다. 발송 흐름(수합/버튼 승인 대기/발송/진행/반환)은 별도 `status`에 기록한다. 포괄적인 “사용자 대기” 상태를 사용하지 않는다.

## 5. 대화 보호와 보고

- 요청 수합·조건 수정·버튼 승인 대기 중에는 현재 주제를 활성 상태로 유지한다.
- 타 작업의 완료 회신은 수신·기록하되 `상태/완료알림큐.json`에 보관한다. 시스템 wake나 worker_done만으로 대화에 완료 안내를 끼워 넣지 않는다.
- 현재 주제가 끝났음을 확인한 뒤 큐를 한 번에 읽어 보고한다. 무응답·경과 시간만으로 주제를 종료하지 않는다. 실제 보고 후에만 보고 완료로 표시한다. 앱 자체의 시스템 알림을 끄는 기능과는 구분한다.
- 결과 보고는 번호/실제 상태/작업명부터 시작한다. 이번에 설명하는 완료 항목은 초록 표시(미지원이면 🟢)를 사용한다. 제작·검증·합격·반영과 근거를 구분한다. 사용자가 단답을 요구하면 짧게 답한다.

## 6. 보존과 저장

- 같은 파일의 동시 편집을 피한다. 기존 원본·미커밋 작업·사용자 승인/반려·실제 송수신 증거를 보존한다. 운영 정리가 기존 작품의 재승인을 뜻하지 않는다.
- 오래된 운영 본문은 활성 규정에서 제거하고 복구용 사본으로만 보관한다. 과거 요청의 실제 모델 제한·판정·작업 ID를 거짓으로 고치지 않는다.
- Git 저장은 사용자 요청 때만 `작업기록 → 검증 → 커밋 → 업로드 → 원격 해시 확인` 순서로 한다. 자동 커밋·푸시를 하지 않는다. 로컬 산출물·운영 기록 작성은 GitHub 저장과 다르다.
