# MAIN01 작업대장 v3 사용법

지시 원본은 `작업/<ID>/통합작업명세.json` 하나다. 상태와 근거는 task.json, 송수신 영수증과 검증 산출물은 별도 증거다. 운영 원본은 [운영규칙](../운영규칙.md)이다.

명령 앞에 `python 작업관리/도구/작업대장.py`를 붙인다.

1. `new --main main01 --branch <역할> --title <제목> --request-file <사용자원문>`: 통합 명세와 상태만 만든다.
2. `update-spec --task <ID> --file <현재조건.json> --correction <정정원문> --source <실제출처>`: 원문과 이전 조건을 동일 명세에 보존하고 차수를 올린다. 승인과 새 차수의 상태는 초기화한다. 입력 파일은 가져오기용이며 운영 원본이 아니다.
3. 현재 조건에는 goal, deliverables, requirements[{id,text,source}], keep, change, references, allowedFiles, checks, professionalPrompt, promptCoverage{요구ID:프롬프트구절}, image26{allowed,userEvidence}, unresolved를 기록한다. 모델·수량·각도·행동 순서를 빠뜨리지 않는다. image26.allowed는 실제 사용자 허가일 때만 true다.
4. 필요한 작품 기준만 `set-readings --task <ID> --file <경로배열.json>`으로 추가한다.
5. `approval-request --task <ID>`는 질문 ID·현재 차수·해시·진행/수정 요청 선택지를 준비한다. 실제 시스템 질문 도구로 명세의 핵심 범위를 제시한다. 이 명령만으로 사용자에게 버튼이 표시된 것은 아니다.
6. **현재 네이티브 클릭 인증 어댑터가 없어서 confirm과 prepare는 실행 차단 상태다.** 일반 입력과 선택 클릭을 식별하는 공식 이벤트 연결이 필요하다. 로컬 JSON·인용문·gate-resolve·AI의 클릭으로 우회하지 않는다. 테스트의 가짜 이벤트 리더는 임시 폴더 검사에서만 사용한다.
7. 인증 연결 이후 `confirm → prepare`가 통과하면 공식 Orca 도구로 같은 통합 명세를 전달하고 실제 영수증으로 `record --action sent --task <ID> --evidence <영수증>`을 기록한다. prepare는 발송이 아니다. 별도 요약 프롬프트를 명령 원본으로 만들지 않는다.
8. 담당은 `read-pack --task <ID>`의 본문을 읽는다. 전체 조직도·다른 작업 기록은 첨부하지 않는다. 명세는 원문·정정·현재 조건을 표시하며 과거 버전은 같은 파일에서 필요 시 조회한다. sha256은 전체 원본 파일 기준이다.
9. 읽기 확인 JSON에 task,iteration,role,workSummary,documents[{path,sha256,applies}],requirementCoverage{요구ID:적용내용}를 기록하고 `start --task <ID> --role <역할> --evidence <ACK>`를 통과한 뒤 착수한다. 이 검사는 누락·버전을 검사하며 의미 이해 자체를 증명하지 않는다.
10. `record --action returned --task <ID> --evidence <반환근거>`는 반환 사실만 기록한다. 제작 완료 여부와 기술 검증은 `stage --task <ID> --stage production|technical --value <상태> --evidence <실제검증>`로 각각 기록한다. worker_done이 자동 합격은 아니다.
11. 사용자 원문으로 `record --action accept|revise --task <ID> --quote <판정> --evidence <출처>`를 기록한다. revise는 피드백 수합이며 수정 제작 허가가 아니다. 새 명세·새 버튼 확인이 필요하다. 실제 반영 증거가 있을 때만 `record --action integrated`한다.

단계값:
- production: not_started / in_progress / complete / partial / failed / unknown
- technical: not_run / in_progress / pass / pass_with_warnings / fail / unknown
- user: not_reviewed / accepted / rejected / unknown
- integration: not_applied / applied / unknown

`list`는 간결한 4단계 상태, `list --full`은 이력 포함 전체 상태를 보여준다. 새 차수의 상태는 이전 결과와 혼동하지 않는다. 과거 48개 작업은 원문을 이관했으나 재발송용 조건 확정은 하지 않았다. 해당 작업을 다시 진행할 때 최신 요청으로 update-spec을 완성한다.

대화 시작 때 `topic --name <현재주제>`로 보호한다. 반환 완료는 큐에 기록된다. 주제가 끝났음을 확인한 뒤 `topic --name <동일주제> --close`, `notifications`로 모아서 읽는다. 실제 보고 후 `notifications --reported <eventId...>`를 실행한다. 조회만으로 알림을 소모하지 않으며 활성 대화 동안 보고 처리도 차단한다. 공식 wake를 받으면 실제 회신을 기록하고 타 주제 완료 공지는 큐에 둔다. 앱 자체의 알림 배너는 이 도구의 제어 대상이 아니다.

현재 연결은 규정과 파일 업데이트이며 열린 모든 AI가 이미 읽었다는 뜻은 아니다. 다음 작업의 ACK/start로 실제 적용을 확인한다. 작업대장은 파일 편집 권한이나 앱의 직접 실행 경로를 강제로 통제하는 보안 경계가 아니다. 공식 디스패치와 외부 생성 전에 MAIN01이 동일 게이트를 지켜야 한다.

검사: `python -m unittest discover -s 작업관리/도구 -p "test_*.py" -v`. 모든 워크플로우 검사는 임시 폴더에서 실행한다. 과거 텍스트 승인 검사들은 백업 후 버튼 승인·명세·상태·큐 검사로 대체했다.
과거 OPS 이관/초기 세팅 스크립트는 현재 운영에 재실행하지 않는다. 폴더를 초기화하거나 규칙을 이전 버전으로 돌리지 않는다. Git 커밋·푸시는 사용자 저장 요청 때만 한다.
