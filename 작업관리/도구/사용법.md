# 작업대장 사용법

이 도구는 공유 기록·확인 근거·발송 준비·충돌을 관리한다. 실제 메시지는 공식 Orca 도구로 발송한다. prepare만으로 실제 전달됐다고 보고하지 않는다. 사용자의 실제 대화 원문은 담당 메인이 정직하게 기록하며, 이 로컬 도구가 발화자 신원을 인증하는 것은 아니다.

1. `new --main main02 --branch ui --title ... --request-file <요청원문파일>`로 작업을 만든다.
2. 생성된 요청확인.md·전문프롬프트.md·2_사전확인.md를 실제 내용으로 완성한다. 시안이 필요하면 먼저 실제 시안과 부분 선택 조합을 보여준다. 해당 작품의 제작기준·최근 피드백 파일을 `set-readings --task ... --main ... --file <경로배열.json>`으로 추가한다. 역할 공통 필독은 자동으로 포함된다.
3. 사용자에게 이해 내용을 제시하고 확인받은 원문·대화 근거 파일을 보존한다. `confirm --task <번호> --main main02 --quote <사용자원문> --evidence <근거파일>`로 기록한다.
4. `prepare --task <번호> --main main02`는 규정·지시 변경과 다른 메인의 브랜치 점유를 검사하고 발송준비-vNNN.json을 만든다. OPS-004 작업은 승인 원문을 보존한 별도 `발송지시-vNNN.md`에 필독 경로와 실행 절차를 자동 첨부한다. 발송준비 파일의 selector와 **prompt가 가리키는 발송지시**를 이용해 Orca의 실제 담당에게 전달한다. 원문 전문프롬프트만 보내서 필독 절차를 누락하지 않는다.
5. 실제 CLI 영수증을 보존하고 `record --action sent --task ... --main ... --evidence <영수증>`으로 연결한다. 이 단계는 영수증 기록이며 제작 완료가 아니다. 송신 실패·불명확한 수신은 실제 영수증과 공식 복구 절차로 판별하고 중복 발송하지 않는다.
6. 수신 담당은 아래 필독 절차에 따라 `read-pack` → 적용 내용 기록 → `start`를 수행한 뒤 작업한다. 담당의 실제 반환 보고를 받은 뒤 `record --action returned ... --evidence <반환보고>`를 기록한다. 현재 차수의 읽기 확인과 문서 버전이 유효해야 사용자 판정 대기로 전환하며 브랜치 잠금을 해제한다. 검토 중인 결과물은 차수별 독립 파일/해시로 보존한다. 후속 작업으로 덮어쓰지 않는다.
7. 사용자 판정 원문으로 `record --action accept|revise ... --quote ... --evidence ...`를 기록한다. revise는 이전 지시·확인을 보존하고 차수를 늘리며 확인을 초기화한다. 수정 지시를 다시 확인받은 뒤 prepare한다.
8. 통합의 실제 증거를 보존하고 accepted 상태에서만 `record --action integrated ...`를 기록한다. 이 명령이 파일 통합·Git 커밋·푸시를 실행하지는 않는다.

명령 앞에는 `python <공유원본>/작업관리/도구/작업대장.py`를 붙인다. `list`는 전체 작업을 JSON으로 보여준다. 공유 상태는 작업별 task.json이며 다른 메인 소유의 작업을 임의 변경하지 않는다.

writer.lock은 짧은 기록 갱신 잠금이다. 남은 잠금을 시간 경과만으로 삭제하지 말고 실제 소유 프로세스와 Orca 작업 종료 여부를 확인한다. 시작·반환이 불명확한 작업은 근거를 확인한 후 운영자가 회복한다. 자동 강제 해제·자동 재발송은 없다.

검사: `python -m unittest discover -s 작업관리/도구 -p test_workflow.py -v`. 검사는 임시 폴더에서 수행하며 실제 작업 등록·메시지 발송을 하지 않는다.

## 매 작업 하달 후 필독 (OPS-004)

초기 채팅 개설 때 읽었던 것으로 새 작업을 대신하지 않는다. 메인·팀장·테스터·기존 전문 담당에게 모두 적용한다.

1. 수신 에이전트는 `read-pack --task <번호> --main <담당메인>`으로 자기 AGENTS, 작업진행방법, 공통/분야 규정, 작품별 추가 기준을 본문으로 읽는다. `documents`는 현재 해시를 가진 필독 본문이다. `liveContext`의 작업대장·역할 연결도 읽고 병행 작업을 확인한다. 이 상태 자료는 다른 팀의 갱신만으로 읽기 확인을 무효화하지 않는다. 출력이 잘리면 해당 파일을 별도로 전부 열어 읽는다.
2. 실제로 읽은 뒤 JSON 확인서를 작성한다. `task`, `iteration`, `role`은 현재 수신 작업과 같아야 한다. `workSummary`에는 이번 작업 방식, `documents`에는 **모든 필독 문서**의 `path`, `sha256`, `applies`를 쓴다. `applies`는 해당 문서에서 이번 작업에 적용하는 내용이다. 적용하지 않는 조항은 이유를 적는다. 아래 예시의 값은 실제 내용으로 바꾼다.

```json
{
  "task": "MAIN01-20261109-EXAMPLE",
  "iteration": 1,
  "role": "monsters",
  "workSummary": "{{이번 작업의 원본 보존·변경 범위·검증 방법}}",
  "documents": [
    {"path": "{{read-pack의 실제 절대 경로}}", "sha256": "{{현재 해시}}", "applies": "{{이 문서의 작업 적용 내용}}"}
  ]
}
```

3. `start --task ... --main ... --role <수신역할> --evidence <읽기확인.json>`을 실행한다. 실제 발송 영수증 연결이 아직 안 됐으면 담당 메인이 연결한 뒤 재시도한다. 사용자 승인 대기가 아니다. 통과한 확인서는 작업 폴더에 별도로 보존되고 작업이 `in_progress`로 바뀐다.
4. 문서 누락·빈 요약·다른 작업/차수/역할·오래된 해시는 거부된다. `read-pack`만 실행해서는 착수 처리되지 않는다. 도중에 기준이 갱신되면 해당 변경을 읽고 **현재 목록 전체**로 새 확인서를 작성해 `start`를 다시 실행한다. 이전 확인서는 보존한다. 단순 재열람에 사용자 재승인을 요구하지 않는다. 제작 범위 변경은 기존 사용자 확인 절차를 따른다.
5. 현재 읽기 확인 없이 결과 반환이나 잠금 해제를 하지 않는다. 수정 차수는 이전 확인을 재사용하지 않는다. 과거 기록은 유지하며 OPS-004 이전 작업은 새 수정 차수부터 새 정책을 적용한다.

`set-readings` 입력은 UTF-8 JSON 경로 배열이다. 예: `["C:/프로젝트/제작기준.md", "C:/프로젝트/최근피드백.md"]`. 사용자 확인 전 초안에서만 연결한다. 전문 규정이 링크하는 문서 중 이번 작업에 적용되는 기준의 실제 경로를 메인/팀장이 찾아 추가한다. 해당 작품 기준이 아직 없다면 확정된 사용자 지시를 기준으로 삼는다고 전문 지시에 명시한다.

### 메인 자체 작업과 임시 하위 에이전트

메인 자체 분석처럼 작업대장에 등록하지 않은 작업은 자기 작업진행방법·공통 규정·해당 기준을 읽고 사전확인에 문서와 적용 내용을 남긴다. 이를 제작 지시의 사용자 이해 확인이나 팀장 착수 확인으로 재사용하지 않는다.

팀장이 임시 하위 에이전트를 만들 때는 `양식/하위위임.md`로 원작업/차수/하위 작업 ID, 위임한 역할, **하위 담당이 따를 작업 방법**, 필독 절대 경로, 허용 파일, 보고 위치를 전달한다. 등록된 전문 역할이면 해당 작업진행방법을, 새 단기 역할이면 상위 규정 안에서 작성한 세부 작업 방법을 전달한다. 수신 하위 담당도 실제로 읽고 문서 경로·해시·적용 요약을 자기 확인서에 남긴 뒤 작업한다. 팀장은 하위 확인서를 직접 확인하고 원작업 결과에 연결한다. 별도 등록되지 않은 단기 하위 작업이 팀장 역할로 `start`를 대신 호출하거나 팀장의 읽기 확인을 재사용하지 않는다. 등록된 독립 작업에는 동일한 작업대장 게이트를 적용한다.

이 도구는 확인 기록의 누락·버전·작업 연결을 검사한다. 모델의 실제 이해를 증명하거나 도구 밖의 파일 편집을 차단하는 장치는 아니다. AGENTS 시작 지침과 발송문, 작업대장 검사를 함께 사용하고 검수 때 적용 여부를 확인한다. 설정 완료와 실제 수신/필독 완료는 구분한다. 기존 열린 채팅에 공지가 즉시 주입됐다고 보고하지 않는다.

## 도메인 계층

새 작업은 공유 도메인 트리에서 역할 ID를 고른다. 표시 이름과 Git 경로를 구분한다. `python 작업관리/도구/도메인검증.py`는 실제 Orca 관계와 원본 연결을 읽어 검증한다. `도메인정리.py`, `도메인색인.py`, `도메인문서마무리.py`, `도메인최종기록.py`는 OPS-002 이관용이며 이후 트리를 초기화하기 위해 반복 실행하지 않는다. 기존 절차 검사는 test_workflow.py, 도메인 모델 검사는 test_domain_tree.py다.
